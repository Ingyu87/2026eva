# 문서 안내 — 이 폴더의 문서 4개는 각각 무슨 역할인가

> 비개발자용 안내입니다. 개발을 맡기거나 AI에게 작업을 시킬 때
> "어느 문서를 보라고 해야 하는지" 판단하는 데 쓰세요.

---

## 한 문장 요약

집을 짓는다고 생각하면 이렇습니다.

| 문서 | 집짓기에 비유하면 | 답하는 질문 | 주로 읽는 사람 |
|---|---|---|---|
| **prd.md** | 건축주 요구사항서 | **왜** 만들고, 누가 쓰고, 무엇이 되어야 하나 | 기획자·의사결정자·나 자신 |
| **design.md** | 인테리어 시안집 | **어떻게 보이나** (색·글꼴·버튼 모양·간격) | 디자이너·퍼블리셔 |
| **spec.md** | 설계 도면 | **무엇이 어떻게 동작하나** (화면·데이터·규칙) | 개발자 |
| **implementation.md** | 공사 일정표 | **어떤 순서로 언제 만드나** | 개발자·진행 관리자 |

---

## 왜 하나로 안 쓰고 4개로 나누나

**바뀌는 속도가 다르기 때문**입니다.

- `prd.md`의 "학교평가서를 자동 생성한다"는 목표는 **거의 안 바뀝니다.**
- `design.md`의 "버튼 색은 이 파랑"은 **가끔 바뀝니다.**
- `spec.md`의 "저장 버튼을 누르면 이 API를 호출한다"는 **자주 바뀝니다.**
- `implementation.md`의 "이번 주엔 3단계"는 **매주 바뀝니다.**

하나의 문서에 다 넣으면, 일정 하나 바꾸려고 열었다가 목표까지 흔들리게 됩니다.
나눠두면 **바뀐 부분만 고치고 나머지는 건드리지 않습니다.**

또 하나, **AI에게 작업을 시킬 때 유용합니다.**
"디자인만 고쳐줘" → `design.md`만 주면 됩니다. 엉뚱한 곳을 건드리지 않습니다.

---

## 1. prd.md — 제품 요구사항 문서 (Product Requirements Document)

### 무엇을 적나
- 지금 뭐가 문제인가 (예: 부장님들 작업이 사라진다)
- 그래서 무엇을 만들 것인가 (예: 결과를 넣으면 보고서 3종이 나온다)
- 누가 쓰는가, 어떤 상황에서 쓰는가
- **무엇을 안 만들 것인가** (이게 의외로 제일 중요합니다)
- 다 만들었다고 판단하는 기준

### 무엇을 안 적나
- 화면이 어떻게 생겼는지 ❌ → `design.md`
- 어떤 기술을 쓰는지 ❌ → `spec.md`
- 언제까지 만드는지 ❌ → `implementation.md`

### 판단 기준
> "이거 **왜** 만들어요?" 라는 질문에 답이 되면 PRD.
> "이거 **어떻게** 만들어요?"에 답하면 PRD가 아닙니다.

### 나에게 중요한 이유
개발 도중 "이 기능도 넣을까요?" 소리가 나올 때,
**PRD의 '비목표' 항목을 펴서 "그건 이번엔 안 합니다"라고 말할 수 있습니다.**
이게 없으면 일정이 무한히 늘어납니다.

---

## 2. design.md — 디자인 시스템 문서

### 무엇을 적나
- 색: 주 색상, 배경색, 글자색, 경고색 (실제 색상 코드로)
- 글꼴: 종류, 크기 단계, 굵기
- 간격: 여백을 8px 단위로 쓸지 4px 단위로 쓸지
- 모서리 둥글기, 그림자
- 부품(컴포넌트) 규격: 버튼·카드·탭·토글·입력창이 각각 어떻게 생겼는지
- 화면 배치 규칙: 사이드바 너비, 상단바 높이

### 무엇을 안 적나
- 그 버튼을 누르면 무슨 일이 일어나는지 ❌ → `spec.md`

### 판단 기준
> **"눈에 보이는 것"만** 적습니다. 동작은 적지 않습니다.

### 나에게 중요한 이유
이 문서가 없으면 **화면마다 파란색이 조금씩 다릅니다.**
어떤 버튼은 모서리가 8px, 어떤 건 12px이 됩니다. 사용자는 이유는 모른 채
"뭔가 조잡하다"고 느낍니다. 지금 앱이 "직관적이지 않다"는 평을 듣는 이유 중 하나입니다.

그리고 나중에 **"교육청 클래스보드랑 똑같이 맞춰주세요"** 같은 요청을
말로 설명할 필요 없이 이 문서를 넘기면 됩니다.

---

## 3. spec.md — 기능 명세서 (Specification)

### 무엇을 적나
- 화면이 몇 개 있고, 각 화면에 무엇이 놓이는가
- 무엇을 누르면 무슨 일이 일어나는가
- 저장되는 데이터가 어떻게 생겼는가 (항목 이름과 종류)
- 서버와 주고받는 규칙(API) 목록
- 계산식 (예: 영역 평균점수 구하는 공식)
- 예외 상황 처리 (예: 두 사람이 같은 문항을 동시에 고치면?)

### 무엇을 안 적나
- 왜 이 기능이 필요한지 ❌ → `prd.md`
- 색깔과 폰트 ❌ → `design.md`

### 판단 기준
> 개발자가 이것만 보고 코드를 짤 수 있으면 완성된 spec입니다.
> 중간에 "이건 어떻게 하죠?"라고 물어야 하면 아직 빈 곳이 있는 겁니다.

### 나에게 중요한 이유
**"만들고 보니 내가 생각한 거랑 다르다"를 막는 문서**입니다.
코딩 전에 글로 먼저 맞춰보면, 다 만든 뒤 갈아엎는 것보다 훨씬 쌉니다.

특히 이번 프로젝트는 **계산식이 규정으로 정해져 있습니다.**
(가이드북 51쪽의 영역 평균점수 공식) 이건 반드시 spec에 박아두고
"이 공식대로 나오는지" 검사해야 합니다. 틀리면 교육지원청에 잘못된 숫자가 제출됩니다.

---

## 4. implementation.md — 구현 계획서

### 무엇을 적나
- 전체를 몇 단계로 쪼갤 것인가
- 각 단계에서 무엇을 만들고, **무엇이 되면 끝난 것으로 볼 것인가**
- 어떤 순서로 해야 하는가 (A를 먼저 해야 B를 할 수 있는 관계)
- 막힐 위험이 있는 지점과 대비책
- 어떤 파일을 손대게 되는가

### 무엇을 안 적나
- 기능의 상세 동작 ❌ → `spec.md`

### 판단 기준
> "지금 우리 어디까지 했죠?"에 답할 수 있으면 됩니다.

### 나에게 중요한 이유
- **위험을 미리 봅니다.** 예: 2026 엑셀 서식을 못 구하면 그 기능은 아예 못 만듭니다.
  이걸 8단계에서 알면 늦고, 0단계에서 알면 미리 공문을 넣을 수 있습니다.
- **중간에 멈춰도 쓸 수 있게** 순서를 짭니다. 저장 문제 해결이 1단계인 이유가 이겁니다.
  지금도 매일 데이터가 사라지고 있으니까요.

## 실제로 어떻게 쓰나

| 상황 | 여는 문서 |
|---|---|
| "이 기능 꼭 필요한가?" 싶을 때 | prd.md |
| 개발자/AI에게 일 시킬 때 | spec.md + design.md |
| "지금 어디까지 됐지?" | implementation.md |
| 화면이 어색해 보일 때 | design.md |
| 새 요구가 들어왔을 때 | prd.md에 먼저 적고 → spec.md 수정 → implementation.md에 일정 반영 |

**수정 순서를 지키세요.** prd → spec → implementation 순입니다.
거꾸로 하면(일정부터 바꾸면) 왜 그렇게 정했는지 아무도 모르게 됩니다.

---

## 문서 간 관계

```
prd.md          왜 / 무엇을
   │
   ├──► design.md         어떻게 보이나
   │         │
   └──► spec.md ◄─────────┘   무엇이 어떻게 동작하나
             │
             └──► implementation.md   어떤 순서로 만드나
```

`spec.md`는 `prd.md`의 목표를 화면과 규칙으로 옮긴 것이고,
`design.md`의 부품을 가져다 씁니다.
`implementation.md`는 `spec.md`를 작업 순서로 쪼갠 것입니다.
