### 1.1 역할 분담 — Upstage vs Gemini

두 AI를 쓰는데 하는 일이 다릅니다. 섞지 않습니다.

| 도구 | 하는 일 | 안 하는 일 |
|---|---|---|
| **Upstage** | 문서를 **구조화된 데이터로 바꾸기** (표·필드 추출) | 해석·판단 |
| **프로그램** | 점수 **계산**, 4단계 판정 | — |
| **Gemini** | 계산된 숫자와 글을 **해석** | 계산, 문서 파싱 |

```
PDF/XLSX  ──Upstage──▶  구조화 JSON  ──프로그램──▶  집계 수치  ──Gemini──▶  해석 문장
```

### 1.2 Upstage API 사용 원칙

- **`extract_information`(필드 추출)을 우선** 씁니다. `parse_document`(전문 파싱)는 구조를 모를 때만.
  전문 파싱은 결과물이 크고, 결국 우리가 원하는 필드만 골라야 하므로 두 번 일입니다.
- 추출 결과는 **항상 파일로 저장**합니다. 메모리나 대화로 흘리지 않습니다.
- 추출 후 반드시 **검증 단계**를 거칩니다 (4.1의 정규화·허용 목록 대조).
  Upstage도 완벽하지 않습니다. 실제로 예시자료 PDF에서 페이지 경계 유령 행 4개가 확인되었습니다.
- 환경변수: `UPSTAGE_API_KEY`

## 4. 핵심 규칙

### 4.1 문항 풀 적재

교육청 `1_(초)2026 학교평가 평가문항 예시 자료.xlsx`의 대상별 4개 시트를 읽습니다.
교원 272개, 학부모 246개, 학생 217개, 직원 228개로 총 963개입니다.

- `scripts/import-question-workbook.mjs`로 JSON을 생성합니다. 원문 문항은 바꾸지 않습니다.
- 문항마다 대상(`audience`), 원본 시트·행, 자료 해시를 보존합니다.
- 화면에서는 선택한 대상의 원문 문항만 표시하고 담습니다.
- 영역·세부영역 기준은 `src/lib/evaluationFramework.ts` 하나입니다. 원본의 번호 오기는 세부영역 전체 명칭과 대조해 정규화합니다.
- 교원 문항의 기존 식별자는 유지해 저장된 설문과 연결이 끊어지지 않게 합니다.

### 4.2 동시 작업 — 저장 단위를 쪼갠다

**이것이 데이터 유실 해결의 핵심입니다.**

```
변경 전 (문제)
  surveyDrafts/{draftId}
    └ itemsByAudience: { teacher:[…], parent:[…], student:[…], staff:[…] }
      → 문항 1개만 바꿔도 4개 대상 전체를 덮어씀

변경 후
  surveyDrafts/{draftId}                  ← 메타만 (제목·안내문·모드·작성분담)
  surveyDrafts/{draftId}/items/{itemId}   ← 선택 문항 1개 = 문서 1개
```

Firestore는 **문서 단위로 원자성**을 보장합니다. 문서를 쪼개면 충돌이 구조적으로 사라집니다.

- 다른 대상 편집 → 다른 문서 → **충돌 없음**
- 같은 대상, 다른 문항 → 다른 문서 → **충돌 없음**
- **같은 문항 동시 수정할 때만** 충돌 → 4.3으로 처리

### 4.3 순서(order) — 분수 인덱스

> ⚠️ 현재의 `normalizeOrder()`(전체에 1,2,3… 재부여)는 **반드시 제거**합니다.
> 한 명이 순서를 바꿀 때마다 모든 항목이 충돌합니다. 문서를 쪼개도 이걸 두면 소용없습니다.

```
A(1.0)  B(2.0)  C(3.0)

B를 맨 앞으로   →  B.order = 0.5              ← B 문서 1개만 씀
A와 B 사이 삽입 →  new.order = (1.0+2.0)/2    ← 신규 1개만 씀
맨 끝에 추가    →  new.order = max + 1.0
맨 앞에 추가    →  new.order = min - 1.0
```

- 이동·삽입 시 **자기 문서 1개만** 씁니다
- 두 값의 차이가 `1e-6` 미만이 되면 서버가 조용히 재정규화 (드묾)
- **화면 번호는 렌더링 때 계산하고 저장하지 않습니다**

### 4.4 낙관적 잠금

- 모든 `item` 문서와 `draft` 메타에 `rev: number`
- 수정 요청에 `expectedRev`를 함께 보냄
- 서버는 **Firestore 트랜잭션**으로 현재 `rev`와 비교
  - 같으면 → 저장하고 `rev + 1`
  - 다르면 → `409 Conflict` + 현재 문서 반환
- 클라이언트는 이렇게 안내합니다

```
⚠ 이 문항은 김OO 선생님이 2분 전에 수정했습니다.
   [내 수정으로 덮어쓰기]  [상대 수정 유지]  [나란히 비교]
```

**말없이 덮어쓰는 경로는 코드 어디에도 두지 않습니다.**

### 4.5 실시간 반영

#### 커서는 `rev`가 아니라 서버 타임스탬프

> ⚠️ `rev`는 문서마다 **따로 도는 카운터**입니다. 메타의 `rev=3`과 어떤 문항의 `rev=3`은
> 아무 관계가 없습니다. 그래서 `?since={rev}`로는 "어디까지 받았는지"를 표현할 수 없습니다.
>
> **`rev` = 충돌 감지 전용**, **커서 = 서버 타임스탬프**로 역할을 나눕니다.

- 모든 쓰기가 `updatedAt`을 **`FieldValue.serverTimestamp()`** 로 기록합니다.
  서버 시계 하나만 쓰므로 기기 간 시각 차이 문제가 없습니다.
- 삭제는 문서를 지우지 않고 **`deleted: true` 표식**을 남깁니다 (tombstone).
  안 그러면 동기화가 삭제를 알아챌 수 없습니다. 30일 뒤 일괄 정리합니다.

```
GET /api/draft/sync?since=2026-09-18T05:12:33.481Z

응답
{
  "nextSince": "2026-09-18T05:12:36.902Z",   ← 서버가 준 값을 그대로 다음에 되돌려 보냄
  "meta":     { …변경됐을 때만… } | null,
  "changed":  [ …updatedAt > since 인 문항… ],
  "deleted":  [ "itemId", … ],
  "presence": [ … ]
}
```

- 첫 호출은 `since`를 생략합니다 → 전체를 받습니다
- 쿼리: `items.where("updatedAt", ">", since).orderBy("updatedAt")`
  → **복합 색인 필요** (`updatedAt` 오름차순)

#### 폴링 규칙

- **3초 간격**. 브라우저 탭이 비활성이면 **15초**
- **내가 편집 중인 항목은 덮어쓰지 않고** 뱃지로만 알림
- 같은 요청에 presence heartbeat를 실어 보냄: `{ audience, editingItemId }`

> 나중에 Firebase 클라이언트 SDK + `onSnapshot`으로 바꿀 수 있지만,
> 인증 구조를 Custom Token으로 바꿔야 하므로 v2에서는 하지 않습니다.

### 4.5.1 사용자 라벨 — 누가 누군지 구분하는 법

> **문제:** 로그인 계정은 `학교 이름 + 비밀번호` **하나**입니다.
> 세션에도 `{ role, schoolId, schoolName }` 뿐이라 **개인을 구분할 수단이 없습니다.**
> 그런데 접속자 표시와 충돌 안내에는 "누가"가 필요합니다.

**해결: 로그인 직후 한 번 묻습니다.**

```
┌────────────────────────────────────┐
│  누구신가요?                        │
│  같이 작업하는 분들에게 표시됩니다.    │
│                                    │
│  [교무부장        ▾]  ← draftAuthors에서 선택
│  또는 직접 입력 [____________]       │
│                                    │
│  [ 시작하기 ]   [ 익명으로 ]         │
└────────────────────────────────────┘
```

- 선택지는 **기존 `draftAuthors`** (교무부장·교육연구부장·생활인성부장 …)에서 가져옵니다.
  이미 "작성 분담" 기능이 쓰는 목록이라 별도 데이터가 필요 없습니다.
- 직접 입력도 가능합니다 (최대 20자)
- `localStorage["school-eval-display-name"]`에 저장 → 다음 접속부터 안 묻습니다
- 상단바 `⚙설정`에서 언제든 바꿀 수 있습니다
- **건너뛰면** `사용자 2` 처럼 세션 순번으로 표시합니다

**보안 경계 — 이것은 인증이 아닙니다.**

- 표시용 라벨일 뿐이며 위조할 수 있습니다
- 권한 판단·접근 제어에 **절대 쓰지 않습니다.** 권한은 학교 세션 쿠키로만 판단합니다
- 학교 내부 협업 도구이므로 이 수준으로 충분합니다

**저장 위치**

- 클라이언트: `localStorage`
- 서버: `presence` 문서의 `displayName` (30초 지나면 만료)
- 문항 문서의 `updatedBy`에 **마지막 수정자 라벨**을 함께 기록
  → 충돌 안내에서 `김OO 선생님이 2분 전에 수정했습니다` 를 만들 때 씁니다

### 4.7 영역 커버리지 검증

가이드북 Q9에 따라 **학생·학부모·교원은 Ⅰ·Ⅱ·Ⅲ 전 영역에 문항이 있어야** 합니다. 직원은 예외입니다.

- 우측 하단에 실시간 표시
- 비어 있는 영역: 빨강 + `⚠ Ⅲ영역 문항이 없습니다`
- **구글폼 만들기 / 제출 서류 생성 시 경고.** 단, 막지는 않고 확인만 받습니다
  (특수학교 등 예외 상황이 있을 수 있으므로)

### 4.8 점수 계산 (가이드북 p.51)

> **이 계산은 AI가 아니라 프로그램이 합니다.** 단위 테스트 필수입니다.

```
문항 평균 = Σ(응답자 수 × 척도값) / 문항 전체 응답자 수

영역 평균 = Σ(영역 응답 소계 × 척도값) / 영역 문항 응답 합계
```

**⚠️ 영역 평균은 문항 평균들의 단순 평균이 아닙니다.** 영역 전체 응답을 모아 구한 가중평균입니다.

**척도값 매핑 — 반드시 라벨 기준**

```
"매우 그렇다"    → 5
"그렇다"        → 4
"보통이다"      → 3
"그렇지 않다"    → 2
"전혀 그렇지 않다" → 1
```

> ⚠️ 저장소의 `2026학년도 1학기 … 설문.json`은 `value 1 = 매우 그렇다`로 **뒤집혀** 있습니다.
> 구글시트에는 라벨 문자열이 들어오므로 **반드시 라벨 → 점수 표로 변환**합니다.
> 순서·인덱스 기반 계산은 금지합니다. 이걸 놓치면 4.9점이 최악 평가가 됩니다.

**4단계 환산** — 반올림 전 원값으로 판정. 화면 표시만 소수 둘째 자리에서 반올림

| 평균 | 판정 |
|---|---|
| 4.0 이상 | 매우 우수 |
| 3.0 이상 ~ 4.0 미만 | 우수 |
| 2.0 이상 ~ 3.0 미만 | 보통 |
| 2.0 미만 | 미흡 |

**검증 케이스 (반드시 통과)** — 가이드북 51쪽 예시

```
입력: 5점 113명, 4점 35명, 3점 16명, 2점 7명, 1점 4명 (합 175)
계산: (113×5 + 35×4 + 16×3 + 7×2 + 4×1) / 175 = 771 / 175 = 4.405
반올림: 4.4
판정: 매우 우수
```

### 4.10 전년도 학교평가서 읽기 (신규)

환류가 작동했는지 확인하려면 **작년 평가서의 개선과제**가 필요합니다.
학교가 작년 평가서 파일(PDF·DOCX·HWP)을 올리면 **Upstage `extract_information`** 으로 구조화합니다.

```json
{
  "schema": {
    "type": "object",
    "properties": {
      "schoolName": { "type": "string" },
      "year":       { "type": "string" },

          "type": "object",

            "area":     { "type": "string" },

            "grade4":   { "type": "string", "description": "매우 우수/우수/보통/미흡" }
          }
        }
      },
      "findings": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "area":     { "type": "string" },
            "subarea":  { "type": "string" },
            "category": { "type": "string", "description": "우수한 점 / 개선할 점" },
            "content":  { "type": "string" },
            "plan":     { "type": "string", "description": "향후 추진계획" }
          }
        }
      },
      "overallOpinion": { "type": "string" }
    }
  }

```

**화면**: S3 설정 모달에 `전년도 평가서 올리기` 추가.
추출 결과를 표로 보여주고 사용자가 수정할 수 있게 합니다.

**저장**: `surveyDrafts/{draftId}/priorReport/{docId}`

**AI 활용**: Gemini가 작년 `plan` 항목별로 올해 점수 변화를 대조해
*"작년 개선과제였던 예산 투명성이 학부모 3.91 → 4.08로 개선됨"* 같은 문장을 만듭니다.

**수행할 분석** — `prd.md` 6장의 7가지

**출력 형식** (구조화 JSON, 자유 산문 금지)

```json
{
  "areas": [{
    "area": "Ⅰ. 협력적 학교자치문화",
    "findings": [{
      "category": "개선할 점",
      "subarea": "Ⅰ-3. 공감과 소통의 행정",
      "indicator": "예산 편성·운영의 적정성 및 투명성 제고",
      "content": "교원과 학부모 간 인식 차가 크게 나타났다. …",
      "cause": "예산 집행 내역의 공개 경로가 제한적이다.",
      "action": "예산 사용 내역 정기 공개, 예산위원회에 학부모 참여 확대",
      "evidence": [
        { "questionId": "q-17", "subject": "학부모", "value": 4.08 },
        { "questionId": "q-17", "subject": "교원",   "value": 4.92 }
      ]
    }]
  }],
  "consultingNeeds": [],
  "featuredCases": [],
  "overallOpinion": "…"
}
```

- `category`는 서식3-1의 세 구분과 1:1 대응: `우수한 점` / `개선할 점` / `컨설팅장학 등 교육청 지원이 필요한 부분`
- **`evidence`는 필수**

**환각 방지 후처리**

1. 생성된 모든 `evidence.value`가 실제 집계 결과에 있는지 대조
2. `content` 본문에 등장하는 숫자를 정규식으로 뽑아 집계 결과와 대조
3. 하나라도 안 맞으면 그 `finding`만 재생성 (최대 2회)
4. 3회째도 실패하면 해당 항목을 비우고 화면에 `⚠ 확인 필요` 표시

**개인정보 처리**

- 선택적 AI에는 학교명·문항·집계 점수와 직접 입력한 학교 활동만 보냅니다. 서술형 응답 원문은 보내지 않습니다. 학교 활동의 연락처 등은 추가 가림 처리하되 개인정보를 입력하지 않도록 안내합니다.
- 사용자에게 사전 고지 + 동의 체크
- 응답 원본·집계는 생성 후 30일간 조회할 수 있습니다. 만료 자료는 다음 조회 때 삭제합니다. 학교 담당자는 결과 화면에서 즉시 삭제할 수 있습니다. 예약 삭제를 구현한 것으로 설명하지 않습니다.

#### 왜 `audience`가 배열이 아닌가

한 문항을 여러 대상에 담을 때 **`audiences: Audience[]` 하나로 묶으면 안 됩니다.**
두 가지가 깨집니다.

**(1) 순서가 공유됩니다.**
교원용에서 3번이면 학부모용에서도 3번이 됩니다. 교원용 순서를 바꾸면 학부모용도 따라 바뀝니다.
실제로는 대상별 설문지 순서가 달라야 합니다.

**(2) 문장을 대상별로 다르게 쓸 수 없습니다. ← 이게 더 큽니다.**
가이드북 41쪽이 **같은 지표라도 대상에 맞는 용어로 다르게 서술하라**고 명시합니다.

```
학생용   "우리 학교는 학생들의 특성과 희망을 반영하여 교육활동을 운영한다."
학부모용 "학부모 간담회, 워크숍, 설문 조사 등을 통해 학부모의 의견을 적극 반영하여
          교육과정을 편성·운영한다."
```

배열 하나에 문장 하나면 이걸 표현할 방법이 없습니다.

**그래서: 여러 대상에 담으면 문서가 복제됩니다.**

```
예시문항 1개  ──[교원·학부모에 담기]──▶  문서 2개 생성
                                        ├ {audience:"teacher", groupId:"g1", order:3.0}
                                        └ {audience:"parent",  groupId:"g1", order:5.0}
                                          → 각자 순서·문장을 따로 수정
```

`groupId`는 이럴 때 씁니다.
- 가이드북 p.40 "평가 주체별 평가지표 구성" 매트릭스 (지표 × 4주체 `○`)
- 서식3-2의 `평가주체` 열
- 평가지표 및 현황 XLSX의 주체별 문항 수 집계

`groupId`가 같은 문서들을 모아 `audience` 목록을 만들면 됩니다.
**저장 단위는 그대로 "문서 1개 = 문항 1개"** 라 4.2의 충돌 회피도 그대로 유지됩니다.

```ts
  aiAnalysis?: AiAnalysis;    // 4.9 출력 JSON
  aiGeneratedAt?: string;
};

type QuestionStat = {
  questionId: string;
  audience: Audience;
  grade?: number;                       // 학생일 때
  distribution: [number, number, number, number, number];  // 5점 → 1점
  responseCount: number;
  mean: number;
};

type AreaStat = {
  area: string;
  audience: Audience;
  subtotal: [number, number, number, number, number];
  mean: number;                          // 반올림 전
  meanRounded: number;                   // 소수 첫째 자리
  grade4: "매우 우수" | "우수" | "보통" | "미흡";
};
```

#### 템플릿 자동 인식 (필수)

> ⚠️ **셀 주소를 코드에 하드코딩하지 않습니다.**
> 2026에서 Ⅲ-2·Ⅲ-3이 통합되므로 행 번호가 확실히 밀립니다.
> 하드코딩하면 2026 템플릿 교체 시 전부 다시 짜야 합니다.

```ts
type TemplateMap = {
  sheetMain: string;                 // 찾아낸 시트명
  sheetSummary: string;
  headerRow: number;                 // '평가 주체별 문항 수' 헤더 행
  subjectCols: Record<Audience, number>;      // 문항 수 열
  resultCols: Record<Audience, number>;       // 4단계 판정 열
  schoolNameCell: string;
  subareas: Array<{
    subarea: string;
    indicatorRows: Array<{ indicator: string; row: number }>;
    etcRow: number;                  // '기타 :' 행
    totalRow: number;                // '합계' 행
  }>;
  areaResultRows: Record<string, number>;     // 영역별 판정 기입 행
};
```

**인식 절차**

1. 시트 목록에서 본표 시트와 집계 시트를 찾는다 (시트명 대신 헤더 문자열로 판별)
2. `평가 주체별 문항 수` / `평가 주체별 평가 결과` 헤더를 찾아 행·열 위치 확정
3. 세부영역 열을 위에서 아래로 훑어 `Ⅰ-1` ~ `Ⅲ-4` 위치를 수집
4. 각 세부영역 구간에서 평가지표 이름과 행 번호, `기타 :` 행, `합계` 행을 수집
5. 학교명 입력 칸을 찾는다 (`학교명:` 라벨 우측 셀)

**검증 및 저장**

- 인식 결과를 `templates/{basename}.map.json`으로 저장해 재사용
- 세부영역이 10개 미만이거나 주체 열을 4개 못 찾으면 **수동 연결 화면**으로 넘김
- 관리자 화면에 인식 요약 표시

```
✔ 템플릿 인식 완료
   세부영역 10개 · 평가지표 47행 · 주체 열 4개 · 시트 2개
   [이대로 사용]   [수동으로 맞추기]
```

**템플릿 경로**

```
templates/
  indicator-status-2025.xlsx       ← 개발·테스트용 (현재 보유)
  indicator-status-2026.xlsx       ← 확보 시 여기에 배치
```

앱은 **가장 최신 연도 템플릿**을 기본으로 쓰고, 관리자가 바꿀 수 있습니다.

### 후속 보완: 결과 구분과 내부 검토

결과에 선택 입력 `label`(60자), `review.note`(5,000자), `review.checked`를 저장한다. `PATCH /api/results`는 학교 담당자만 사용하며 `expectedUpdatedAt`을 트랜잭션에서 검사한다. 의견 변경 시 검토 체크는 해제한다. 검토 기록은 학교 내부 관리용이며 제출 요건을 추가하거나 공식 서식에 넣지 않는다.
결과 화면은 단계별 접기·이동을 지원하고 접힌 입력란은 마운트 상태를 유지한다. 문서에서 수정한 내용은 앱으로 자동 반영되지 않음을 안내한다.

### 작년 설문으로 시작하기 (2026-09-19)

빈 설문의 첫 진입과 학년말 시작 화면, 설문 설정에서 PDF 최대 4개(각 12MB)를 함께 선택한다. 파일별 추출 실패는 다른 파일의 결과를 지우지 않는다. 파일명에서 교원·직원·학생·학부모(보호자)를 인식하고 파일 전체 또는 문항별 대상을 수정할 수 있다. 대상별 탭에서 원문·보기·응답 유형·올해 세부영역을 확인한다. 문항 제외가 가능하며 유형이 불명확하거나 선택형 보기가 불완전하면 담기를 막는다. 고정 척도와 다른 보기는 선택형으로 보존한다. 원본 대조 확인 후 기존 문항을 유지한 채 문항별 아웃박스 저장 경로로 추가한다. 추출은 기존 Upstage/Gemini 설정을 사용하며 외부 전송을 업로드 전에 안내한다.

### 작년 설문 수정 화면 (2026-09-26)

작년 PDF에서 가져온 문항이 있으면 기본적으로 우리 학교 문항만 넓게 표시한다. 새로 접속해도 가져온 문항을 기준으로 같은 화면을 연다. 예시는 ‘예시문항에서 추가’로 펼치고 ‘우리 학교 문항만 보기’로 접는다. 문항 편집·저장·충돌 처리와 부장별 수정 권한은 기존 규칙을 유지한다. PDF 추출 결과의 대상·문항·척도·올해 세부영역 확인은 생략하지 않는다.

### 저장 실패와 기존 문항 담당 배정 (2026-09-26)

- 연속 입력을 합칠 때 새 작업 번호를 부여한다. 앞선 요청의 성공 응답은 새 입력을 삭제하지 않는다.
- 브라우저 임시 저장 실패 시 현재 탭 메모리에 작업을 유지하고 서버 전송을 계속한다. 미저장 상태에서는 창 이탈 경고와 텍스트 파일 보관 수단을 제공한다. 메모리 보관은 창을 닫은 뒤 복구를 보장하지 않는다.
- 권한 거절 작업은 보관하고 정상 작업은 계속 처리한다. 거절 건이 남으면 저장 성공으로 표시하지 않는다. 재시도와 사용자가 확인한 거절 내용 취소를 제공한다.
- 연구부장은 문항을 선택하고 ‘담당 부장 배정’에서 같은 학교·같은 대상의 활성 링크에 배정한다. 서버는 모든 문항 버전과 링크 상태를 한 트랜잭션에서 확인한다. 충돌 시 전부 배정하지 않는다. 일반 부장의 배정 요청은 거부하며 기존 문항 소유권 검사는 유지한다.

### 공동 작업 표시와 응답자용 설문 (2026-09-26)

- 수정·확인 기록이 없는 문항은 붉은색과 ‘미확인’ 글자로 표시한다. 기존 자료에 기록이 없으면 과거 수정 여부를 추측하지 않는다.
- 부장 링크를 만들 때 서버가 사용 횟수가 가장 적은 색상 중 하나를 무작위로 배정한다. 색상 선택 항목은 제공하지 않으며, 배정된 색상과 기존 링크·과거 기록의 색상은 유지한다. 붉은색은 미확인 상태에만 사용한다.
- 문항·보기·유형·분류·담당부서가 바뀌면 서버가 실제 작업자의 역할 이름, 색상, 시각을 기록한다. 순서 이동·담당 배정만으로 미확인을 해제하지 않는다. ‘원문 그대로 확인 완료’는 수정과 구분한다.
- 작업 상태는 문항별 동기화로 전달한다. 서로 다른 문항은 동시에 편집하고 같은 문항의 버전 충돌은 사용자가 선택한다.
- 응답자용 DOCX·Google Forms에는 작업자, 수정 시각, 담당 색상, 내부 평가지표 설명을 넣지 않는다. 설문 제목·대상별 안내·문항·보기·학생 학년 분류는 유지한다. DOCX는 한글에서 편집하는 파일이며 HWP 직접 출력과 구분한다.
